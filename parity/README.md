# GLMM parity evaluator

Fits the **same statistical model on the same data** with **R `lme4`**, **Julia
`MixedModels.jl`**, and (later) the Rust `glmm` crate, then compares **estimates**
(correctness) and **fit-time** (speed). Built **R + Julia first, Rust last**: the
reference truth lives where the datasets live. Two independent reference engines
agreeing within tolerance is the strong-truth condition `glmm` is later held to.

## The oracle is sacred

> The committed `data_empirical/*.csv`, the fixed-seed `data_simulated/*.csv`, and
> the R / Julia result JSONs regenerated from them **are** the frozen oracle. When `glmm` is
> later compared against them, on any disagreement
> **`glmm` is presumed wrong** — investigate and fix `glmm`. A reference result is
> regenerated **only** if the reference *model spec* itself is proven wrong (wrong
> formula, family, link), with a recorded justification. **Never** relax a tolerance
> or edit a reference to make `glmm` pass.

The freeze is the committed **inputs**: `data_empirical/*.csv` are committed
byte-for-byte; `data_simulated/*.csv` are gitignored but pinned by the committed
**seed + `prep/` script** (`run.sh --prep` regenerates them byte-identically). The
reference JSONs (`results/`) are regenerated by `run.sh` each time and are
gitignored, not committed (see Layout below); durable summaries live in `reports/`. A
second guard rides along: `glmm` must match **both** engines; where `lme4` and
`MixedModels.jl` themselves disagree beyond tolerance, that is a recorded **flag to
investigate**, never a silent "pick the closer one." The one known, exempt
disagreement is the GLMM standard-error method split (see Tolerances below).

## Layout

```
manifest.json      single source of truth: curated datasets + per-dataset model (both dialects);
                   optional per-rung fields: `data` (CSV to read when it differs from the rung
                   name -- cbpp_probit reuses the committed cbpp.csv byte-for-byte) and `link`
                   (non-canonical link override -- absent = the family's canonical/default link)
prep/export_data.R pull lme4-origin datasets -> data_empirical/*.csv (committed) + data_simulated/*.csv (gitignored; regen with run.sh --prep)
prep/export_grid.R generate the fixed-seed grid -> data_simulated/grid/*.csv (gitignored; regen with run.sh --prep)
data_empirical/*.csv   neutral input from lme4/nlme-bundled datasets, committed -- EVERY engine reads these bytes
data_simulated/*.csv   neutral input from the sim_* rungs (fixed-seed synthetic designs); GITIGNORED, frozen by committed seed + prep script
oracle/fit.R       read csv + manifest, fit lme4, time fit-only, write results/lme4_{empirical,simulated}/<ds>.json
oracle/fit.jl      same with MixedModels.jl -> results/mixedmodels_{empirical,simulated}/<ds>.json
oracle/fit.rs      glmm harness (Cargo example `parity_fit`) -> results/glmm_{empirical,simulated}/
oracle/fit.py      glmm PYTHON PORT harness (the PyO3 wheel) -> results/glmm_python_{empirical,simulated}/
                   -- same kernel as fit.rs, so it is gated against the RUST row, not lme4 (see Timing)
oracle/fit_port.R  glmm R PORT harness (the fastglmm package) -> results/glmm_r_{empirical,simulated}/
                   -- same kernel as fit.rs, gated against the RUST row (a line-for-line port of fit.py)
results/<engine>_{empirical,simulated}/   ten dirs (lme4/mixedmodels/glmm/glmm_python/glmm_r x empirical/simulated),
                   plus results/grid/ + results/glmm_parallel/; all generated by run.sh -- NOT committed (gitignored)
reports/           durable summaries, COMMITTED: reports/grid/{status_map,eval_ratio,data_profiles}.csv,
                   final_analysis.txt, lme4_todo.txt, report.html (written by analyze_grid.R + grid_report.R)
compare.R          cross-engine agreement GATE (lme4 vs MixedModels vs glmm) + the port gates (glmm vs glmm_python, glmm vs glmm_r)
summarize_timing.R    human-readable timing view (no gate): per-fit medians + speedup vs lme4/mmjl + port overhead (py_gap, r_gap)
summarize_accuracy.R  human-readable accuracy views (no gate): diffs vs lme4 + SE-by-method (5-way)
run.sh             default: fits glmm (Rust) + the Python port + the R port + compare.R vs
                   existing oracle results; --oracles refits lme4 + Julia too; --prep implies
                   --oracles; trailing args restrict every engine that runs to those manifest datasets
Manifest.toml      pinned Julia packages (generated on env setup; commit for reproducibility)
```

This is a **plain part of the GLMM repo** — one repo, one `.gitignore`, no nested
sub-workspace, no isolated `Cargo.lock`. When `fit.rs` lands it is an ordinary part
of the crate's build (example / bench / small bin, decided then).

Rung 18 (`sim_binomial_slope_crossed`) is fit on the Rust side by the
**sparse GLMM driver** (`fit_glmm_sparse`): `classify_design` routes any
design with a slope-carrying extra grouping to `Solver::Sparse` for every
family — the dense NoZ GLMM kernel only ever implemented intercept-only
extras and never sees this shape. The aggregated binomial rows enter as
`prop = incidence/size` with prior `weights = size` (the sparse binomial
path is the one that honors prior weights). The same fit is also gated
in-crate against a frozen lme4 golden
(`fit_sparse_binomial_slope_crossed_matches_lme4` in `src/sparse.rs`,
`goldens/sim_binomial_slope_crossed.json`).

This rung is a **2-way gate only** (lme4 + glmm, no MixedModels.jl): the
pinned MixedModels.jl (v5.7.0) cannot *construct* a
`GeneralizedLinearMixedModel` for two crossed groupings that both carry a
random slope, fit with non-trivial binomial weights (`PosDefException` at
construction, before PIRLS runs — confirmed via controlled experiments to be a
package/version limitation independent of this rung's data). `compare.R`
already treats a missing `results/mixedmodels_{empirical,simulated}/<name>.json`
as `n/a` per-dataset, so this needed no code change either —
`results/mixedmodels_simulated/sim_binomial_slope_crossed.json` is intentionally
absent.

Rung 22 (`cbpp_probit`) is the non-canonical-link rung: same formula and data
as rung 5 (the manifest's `data: "cbpp"` reuses the committed CSV
byte-for-byte; `link: "probit"` overrides the canonical logit in all three
engines). On the Rust side it exercises the Fisher-scoring PIRLS branch and
its tight exit (`PIRLS_TOL_REL_NONCANON`, 1e-8) plus that branch's FD-Hessian
SE interaction — the historical probit failure mode — which no canonical-link
rung reaches.

Rungs 8–9 are the sparse non-Gaussian GLMM's external truth (roadmap step 2):
each trips a real envelope cap (7 crossed extras > `MAX_EXTRA_GROUPINGS`) so
`classify_design` routes it to the sparse solver, and both reference engines fit
the family at Laplace — the strong two-reference condition. The Gamma / NB
siblings (`sim_sparse_gamma` over-width q_g=5, `sim_sparse_nb` over-count) live
in the **goldens track** for now (lme4-only reference in `goldens/`, gated
in-crate, the `sim_gamma_glmm` / `sim_nb_glmm` precedent).

Rungs 23–24 (`sim_gamma` dense, `sim_sparse_gamma`) are the specced Gamma GLMM
promotion of those goldens to curated rungs. The 2026-07-11 attempt was backed
out on two glmm-side failures (the oracle is sacred — nothing was relaxed);
their fates split:

- **Rung 23 (dense) RE-LANDED** after the B1 fix: glmm's public
  `Fit::varcorr`/`stddev_corr` omitted the σ̂² dispersion factor for Gamma
  GLMMs (`assemble_varcorr(..., 1.0)`) while `tau2` *was* σ̂²-scaled, so the
  reported stddevs sat exactly σ̂ (~0.76/0.72) off lme4's VarCorr (after
  rescale they agreed to 1e-3–2e-3). Both call sites now thread
  `family::glmm_sigma_sq` (≡ 1 for the φ≡1 families — a no-op there). β/SE on
  the dense rung were excellent throughout (3e-4 / 1e-4).
- **Rung 24 (sparse) stays backed out**, with the B2 diagnosis CORRECTED
  (2026-07-11 bug-fixes pass): the "sparse optimizer stops short" was a
  misattribution. The formula frontend's parser extracts slope REs before intercept
  REs, so the harness lowers `(1|gp) + (1 + x1+..+x4 | ge)` with **ge as
  primary** (q_p = 5) and `classify_design` routes the **dense** kernel — it
  is the dense joint optimizer that lands ~2e-3 deviance above the
  tolPwrss=1e-13 lme4 optimum (β₀ 2.9e-2 off). The sparse orientation of the
  same model (gp primary — what the in-crate golden hand-builds) lands 2e-4
  above lme4's optimum, β 1.6e-3, green at its golden gates. The overnight
  "7.4e-3 deviance" figure also compared against a default-tolPwrss lme4
  value (the lagged-weights artifact — see TOL history). Separately, the
  sparse FD-Hessian SE truncation found here got its own fix
  (`sparse::SPARSE_FD_STEP_REL`). Re-land needs a user decision: frontend RE
  ordering, routing, or dense-schedule work (campaign-settled).

fit.R keeps omitting `sd_se` for dispersion families — lme4's θ-scale
`stddev_se` is not the stddev-scale SE when σ̂≠1, so gating it would compare
unlike against unlike (glmm's `Fit::stddev_se` documents the same θ-scale
convention). These are **2-way gates** (rung-18 precedent, no `jl_formula`):
MixedModels' dispersion-family GLMM is a documented *different* estimator
(dispersion not profiled into the Laplace objective — measured 2e-2 β /
2e-1 stddev / 2e-1 loglik off lme4 on sim_gamma), so its JSONs stay
intentionally absent.

The NB sibling stays in the goldens track permanently: MixedModels has no
glmer.nb equivalent.

Rungs 25–27 (`sim_binomial_slope1`, `sim_poisson_slope1`, `sim_binomial_slope2`)
are the **vector-RE AGQ datasets** (full-AGQ spec Part 5): a single grouping
factor with a correlated intercept+slope RE (q=2, q=3), sized so the Laplace
bias is visible (small clusters / sparse information). Each dataset carries
**two tiers**: the curated rung here is the ordinary **Laplace anchor (nAGQ=1)**
— a full 3-way gate against the machine-tight glmer/MixedModels Laplace oracle,
validating the mode/curvature substrate — while the **AGQ tier (nAGQ ∈ {7, 11})**
lives in the goldens track (`goldens/sim_*_slope*_agq_k{7,11}.json`, the
`cbpp_agq_k7/k11` pattern) against **GLMMadaptive** (`mixed_model(nAGQ = k)`),
because `glmer` refuses `nAGQ > 1` for vector REs. Those goldens freeze β̂, θ̂
(stddev + correlation) and Hessian SEs — **not** deviance (GLMMadaptive's
logLik constants differ from glmer's devfun convention; the deviance scale is
owned by the in-crate k-convergence invariants). They are gated in-crate
(`src/fit/glmm_tests.rs`) at the empirically calibrated `agq_*` bands in
`tol.R`, and were frozen with **tightened `mixed_model` controls** — the
GLMMadaptive defaults under-converge on the low-information rungs, the same
artifact class as lme4's default `tolPwrss` (see `oracle/fit_m3_goldens.R`).

Each dataset is exported **once** from its canonical source (lme4) to neutral CSV;
Julia and Rust read that CSV, **not** their own ecosystem's built-in copy — this is
what guarantees byte-identical input and sidesteps row-order / factor-coding / NA
differences. The manifest's `factors` list names the columns every engine re-coerces
to categorical (R `factor` / Julia `String` + `DummyCoding`); both use the first
sorted level as the contrast base, asserted in `compare.R` via `coef_names`.

InstEval and salamander are **deferred** — added when their rungs need them.

## Running

```sh
./run.sh                    # fit glmm (Rust) + the glmm Python port + compare vs the EXISTING
                            # lme4/MixedModels results on disk -- R/Julia are NOT refit (they
                            # don't change run to run); fast default for iterating on glmm itself
./run.sh --oracles          # refit ALL FOUR engines (R, Julia, Rust, Python) + compare -- use when
                            # regenerating the oracle (new dataset, new machine, tolerance work)
./run.sh --prep             # regenerate data_{empirical,simulated}/*.csv (sims are gitignored) first;
                            # IMPLIES --oracles (changed data invalidates the old R/Julia

./run.sh --oracles cbpp     # combine: refit all four engines, but only for `cbpp`
```

## Result schema

One file per (dataset × engine), uniform field names so comparison is mechanical:

```jsonc
{ "dataset": "sleepstudy", "engine": "lme4", "engine_version": "1.1-35",
  "family": "gaussian", "reml": true, "rung": 2, "converged": true, "singular": false,
  "coef_names": ["(Intercept)", "Days"],
  "estimates": {
    "beta": [...], "se": [...], "sigma": 25.59, "loglik": -871.81,
    "varcomp": [ { "group": "Subject", "terms": ["(Intercept)", "Days"],
                  "stddev": [24.74, 5.92], "corr": [[1, 0.07], [0.07, 1]] } ] },
  "timing": { "fit_seconds_median": 0.0123, "n_runs": 100, "warmup_discarded": 1,
              "fits_per_sample": 1 } }
  // GLMM rungs split timing by SE method: `fit_seconds_median` is replaced by
  // `fit_seconds_median_rx` and `fit_seconds_median_hessian` (MixedModels emits only
  // _rx -- no Hessian variant). The Hessian SE (FD-Hessian / numDeriv) is the main
  // time consumer; on cbpp glmm's Hessian fit is ~1.9x its Rx fit.
```

The single `se` above is a **gaussian (LMM) rung** — its SE is profiled, one method. On
**GLMM rungs** the Laplace SE has two genuinely different variants, so `se` is replaced by
**`se_hessian`** (keeps the θ–β coupling) and **`se_rx`** (conditional on θ̂, drops it);
MixedModels computes only `se_rx`, so its GLMM files carry that field alone. This is what
lets `compare.R` measure like method against like (see Tolerances). glmm emits both (via
`WaldSe::{Hessian, Rx}`) and now also `loglik`/`df` (`Fit::loglik`/`Fit::df`), gated at the
same `loglik_abs_lmm`/`loglik_abs_glmm` bands as lme4/MixedModels, and at `TOL$port_rel`
against the Python port (the R port omits it — `fastglmm` does not surface `loglik` yet).

Both fit scripts normalize the careful bits to one representation: **`varcomp`** to
the absolute σ scale (lme4 reports variances, MixedModels σ-relative θ); **`loglik`**
to the logLik scale (MixedModels reports the −2·logLik objective); **`reml`** is
honored from the manifest, not just recorded (MixedModels defaults to ML, which
biases varcomp downward — `null` and `sigma` absent on GLMM rungs 5–6). `beta`/`se`
follow fixed-effect design-column order (intercept first); `coef_names` asserts both
engines coded the contrasts identically.

## Timing

Each engine times the **construct-and-fit call** — `lmer(formula, df)`,
`fit(MixedModel, f, df)`, `glmm.fit(data, formula)` — native high-resolution timer,
in-process loop, **discards the warm-up pass** (neutralizes Julia's one-time JIT cost),
reports the **median** of the rest. Model matrices are rebuilt from the formula on every
call, so this span is the same for all four engines. Process startup and CSV load are
excluded (each engine's typed columns / DataFrame are built once, outside the loop).

The Rust glmm harness records **two** medians: `fit_seconds_median*` times `fit_cold`
alone (lowering hoisted out — the solver-isolation number for the per-eval / solve-gap
analyses), and `fit_seconds_median*_full` times `lower + fit_cold` (the construct-and-fit
span above). `summarize_timing.R` reads the `_full` fields so glmm compares same-to-same
with the other three; the other engines have only the single, already-inclusive median.

Real cross-engine numbers need the machine locked (the **user** stabilizes + locks; this
harness only records, never writes CPU sysfs) — until then the field is indicative only.
Timing does not gate correctness.

`summarize_timing.R` prints the recorded median fit time per engine (with the glmm
speedup factor); `summarize_accuracy.R` prints the accuracy diffs vs lme4 and the
SE-by-method tables.

### The Python port (`py` / `py_gap`) — what it does and does not measure

`glmm_python` is **not a fourth implementation**: it is the same Rust kernel reached
through PyO3 (`glmm.fit` → `glmm::formula::lower` → `fit_warm(start=NULL)`, which *is*
`fit_cold`). Two consequences, and they pull in opposite directions:

- **Correctness — gated harder than any other engine.** Same kernel, same lowering,
  deterministic optimizer ⇒ the numbers must be *identical*, so `compare.R` gates the
  port against the **Rust row** at `TOL$port_rel` (a round-off band), not against lme4
  inside the cross-engine bands. Measured 2026-07-16: **exactly 0 on every gated
  quantity, all 26 rungs.** That band is diagnostic at 0 and is never widened — a miss
  means the port fed the kernel something different (swapped column, mis-ordered factor
  level, dropped weights vector), which is precisely the bug class the port's `pytest`
  suite cannot see (it fits fresh random data and asserts only convergence).
- **Timing — same-to-same across all four engines.** Every engine here rebuilds the
  model from the formula on each timed call: lme4 (`lmer(formula, df)`), MixedModels
  (`fit(MixedModel, f, df)`), and the port (`glmm.fit(data, formula)`). The Rust glmm
  harness *also* times `fit_cold` alone with lowering hoisted out — the solver-isolation
  number the per-eval / solve-gap analyses need — but that made it the one engine
  measuring a different span, which inflated `py_gap` (and flattered glmm's `vs_lme4` /
  `vs_mmjl`) on tiny fits by counting Rust lowering against the port. So `fit.rs` records
  a **second, construction-inclusive** timing (`fit_seconds_median*_full` = `lower +
  fit_cold`), and `summarize_timing.R` uses *that* for the glmm column and every speedup.
  Now `py_gap` is the **true port tax** — per-call dict scan, `float()` conversion, and the
  FFI copy — because lowering is timed on both sides and cancels. Both sides carry the
  same codegen (`glmm-python` is a workspace member, so the root `[profile.release]`
  lto/codegen-units applies to the wheel), so the gap is the port, not LTO. The fit-only
  numbers stay in the JSON's `fit_seconds_median*` fields for the solver work.

Measured 2026-07-16 (machine locked), construction-inclusive: the port tax is **a fixed
per-call cost** (dict scan + `float()` + FFI copy) of order tens of µs plus ~0.1 µs per
cell. It is **`~1.0x` on every rung whose fit takes more than a few ms** — VerbAgg,
grouseticks, the sparse rungs all sit at 1.0× (some read 0.8–0.9×, which is run-to-run
noise: same kernel both sides, so the port cannot truly be faster). It only shows above
1× where the whole construct-and-fit is sub-millisecond: worst `cake` ~1.7× (a 136 µs
construct+fit, ~90 µs tax), `Oats`/`Penicillin`/`Dyestuff` ~1.4×. Even those are a
sub-millisecond call end to end. Contrast the pre-fix numbers (cake 4.5×): that gap was
mostly Rust lowering the old comparison charged to Python, not a real port cost.

### The R port (`glmm_r`)

`glmm_r` is the same story as `glmm_python` in a second host language: the `fastglmm`
R package (`GLMM/r/`) reaches the identical Rust kernel through its extendr wrapper,
so `oracle/fit_port.R` is gated against the **Rust row** at `TOL$port_rel` (round-off),
not against lme4. It is a deliberate line-for-line port of `fit.py` — the two harnesses
share `read_csv_path`/`build_data`/`formula_of`/`varcomp`/`median_secs`/`fit_one` shape
for shape, so a divergence in either port's data-prep or formula-rewrite logic surfaces
as a diff between near-identical functions rather than an independently-derived bug.
Results land in `results/glmm_r_{empirical,simulated}/` in the same schema as every other
engine; `compare.R`'s "glmm (Rust) vs glmm_r (port)" section is its gate. `run.sh` runs
it by default (skipped with a message if the package is not installed), and
`summarize_timing.R` charts it in the `r` column with an `r_gap` tax column, exactly as
`glmm_python` gets `py`/`py_gap`. Note `r_gap` runs several times larger than `py_gap` on
the sub-millisecond rungs (Dyestuff, Oats, the intercept-only/3-level sims): that is a real
fixed per-call cost of the extendr/R marshaling path (a few hundred µs), not a timer
artifact — it just dominates the ratio when the fit itself is ~50 µs. It washes out on every
rung whose fit clears ~1 ms, where `r_gap` sits at ~1.0x alongside `py_gap`. (`median_secs`
times with `Sys.time()`, ~2 µs resolution; the earlier `proc.time()` floored at 1 ms and
*hid* this real overhead behind a bogus 0.001 s quantum — see its comment.)

Two R-specific details are load-bearing. **Factor levels are forced to byte order**
(`sort(method="radix")`, = C locale = Rust's `str` ordering), not R's default `factor()`
which sorts by the session's `LC_COLLATE`: the kernel byte-sorts the string columns the
Python port hands it, so to feed the same factor codes the R port must too — otherwise a
grouping factor whose byte and locale orders differ (VerbAgg's `item`) permutes the group
order and perturbs the fit below round-off. **Two rungs are flagged `KNOWN` rather than
gated**: `sim_max_q_slope` and `sim_binomial_slope2`. R's `as.numeric` is not correctly
rounded for some values (`-1.6802662379087` stores one ulp below the value Rust and Python
both produce), and on these two already-multimodal correlated-slope surfaces that one-ulp
input shift selects a neighbouring optimum (~1e-7). It is invisible on the other 24 main +
15 weights rungs (all gate at ~1e-15). `TOL$port_rel` is not relaxed — the two are recorded
as a documented numerical-limit exception, and a miss on any other rung is still a port bug.

Against the reference engines the port is simply fast: on cake it is `py` 226 µs vs
`lme4` 13.7 ms (≈60× faster) and `mmjl` 511 µs (≈2× faster) — construction included on
all three. The port was never the slow one; it only ever looked slow next to the Rust
`fit_cold`-only number, which is now reconciled.

On GLMM rungs the time is **split by SE method** (`t_rx` / `t_hess`): the Hessian SE
is the dominant cost (glmm's FD-Hessian re-solves the Laplace deviance ~O(m²) times;
lme4's `vcov(use.hessian=TRUE)` runs numDeriv), while the Rx SE is one closed-form
Schur solve. The fit underlies both, so the gap between `t_rx` and `t_hess` is the
SE-method cost — on cbpp glmm's Hessian fit is ~1.9× its Rx fit. MixedModels has only
the Rx vcov, so its GLMM time is reported under `t_rx` alone.

**Estimator is pinned to Laplace (lme4 `nAGQ=1`) in this curated sweep.** glmm's GLMM
kernel is glmer-faithful `nAGQ=1` (`src/glmm/mod.rs`), so the cross-engine sweep must be
Laplace to compare like-to-like with it. Adaptive Gauss-Hermite quadrature (`nAGQ>1`,
single scalar RE only) is more accurate but a *different* estimator — on cbpp it shifts
β ~5e-4 and the Hessian SE ~1.2% (converged by nAGQ=10). Notably lme4's AGQ Hessian SE
lands *closer* to glmm's than lme4's own Laplace SE, so that ~0.5% glmm↔lme4 Hessian gap
is partly lme4-Laplace's approximation, not a glmm defect.

AGQ comparison is **not** done here — it lives in the separate **goldens track**
(`oracle/fit_m3_goldens.R` → `goldens/`): lme4 reference fits at `nAGQ=1/7/11` for cbpp
and grouseticks, which glmm's AGQ is validated against in-crate once the M3 kernel
exposes an nAGQ knob. Keeping it out of `results/` leaves the 6-rung sweep un-expanded
(design 6) and sidesteps that AGQ is fundamentally lme4-vs-glmm (the 3-way sweep can't
require it).

## Tolerances (per-quantity, in `compare.R`)

A single threshold can't serve point estimates that agree to ~1e-4 and SEs that
legitimately differ by percent. Starting points, tuned against the first reference
run, recorded in `compare.R` — never relaxed to make an engine pass:

- **β**, **varcomp std-devs** — relative ~1e-3
- **loglik** — absolute on the shared scale, split by family: LMM ~1e-6 (the REML
  criterion is near-exact across engines, ~1e-9 observed); GLMM ~1e-3 (two optimizers
  land ~3e-6 *relative* apart on the same Laplace surface — β/varcomp confirm it is the
  same fit)
- **coef names** — compared with cosmetic formatting normalized (`period2` vs
  `period: 2`); asserts same base / levels / order, which the β gate independently confirms
- **LMM SE** (`se`) — tight ~1e-3 (all engines compute it identically)
- **GLMM SE** — split by **method**, so the comparison is like-for-like (this is what
  removed a spurious ~1–1.5% "gap" that was just lme4-Hessian measured against MM-Rx):
  - **`se_rx`** (conditional on θ̂) — all three engines compute it; gated at ~1e-3 (lme4
    vs MixedModels measured ~2e-4 on cbpp). `glmm`'s `WaldSe::Rx` joins this column.
    `compare.R` also prints **`se_rx:mm`** — the same `se_rx` checked against the *second*
    oracle (MixedModels) instead of lme4. The two references disagree ~2e-4 on their own
    Rx and `glmm` sits on the MixedModels value (`glmm`↔MM ~6e-7 on cbpp, vs lme4 ~2e-4),
    so the vs-lme4 number alone understates `glmm`'s agreement with an independent engine.
    `summarize_accuracy.R`'s per-dataset `Rx max-rel` line shows all three pairwise diffs.
  - **`se_hessian`** (keeps the θ–β coupling) — only lme4 and `glmm` compute it
    (MixedModels has none → shown `n/a`); gated at `se_hessian_rel` 1e-3, same band as
    `se_rx` (measured worst 2e-5, grouseticks). The gate sat at 3e-2 while the frozen
    references carried lme4's lagged-ldL2 `tolPwrss` artifact (~1.3% on cbpp — glmer's
    `Xwts` run one PIRLS iteration behind the mode; the 2026-07-04 hessian-curvature
    diagnosis pinned the gap as lme4's). The references are now generated at
    `tolPwrss = 1e-13` (recorded in each JSON) and `glmm`'s FD runs PIRLS at its tight
    FD-only tol, so the band reflects true engine agreement. `stddev_se_rel` (θ-block
    SE, same joint Hessian) tightened 3e-2 → 3e-3 on the same regeneration (measured
    worst 8e-4, sim_sparse_poisson — the single-step-FD vs numDeriv method floor).
    `glmm`'s default is Hessian.

## The Rust engine (incremental, by rung)

`oracle/fit.rs` (Cargo example `parity_fit`, wired via the `rust` entry in `run.sh`)
reads the same CSVs through the formula frontend (`glmm::formula::lower`) into the
stable `fit_cold` surface, emits the same schema (both `se_hessian` and `se_rx` via
`WaldSe::{Hessian, Rx}`) to `results/glmm_{empirical,simulated}/`, and joins the comparison against
the frozen references.

**Landed (glmm):** rungs 1–23 and 25–27 — the full 1–21 roadmap, 22 cbpp_probit
(non-canonical link), 23 sim_gamma (dense, re-landed after the B1 fix), and the
25–27 vector-RE AGQ Laplace anchors — green against both references, except rung
18 which is the documented 2-way lme4+glmm gate (MixedModels cannot construct
that shape). Only rung 24 (sim_sparse_gamma) stays backed out pending a
glmm-side fix (see the gamma note under "Datasets").
